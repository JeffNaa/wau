Wau Core Documentation

A high-flexibility, plugin-driven development platform. Stable Core, Dynamic Business.

Introduction

Wau (Moon Kite) is a high-flexibility, plugin-driven development platform built with NestJS. The core philosophy is "Stable Core, Dynamic Business":

  • Isolate Changes: All business logic lives in plugins; the Core never contains hard-coded logic for specific requirements.
  • Plug & Play: Dynamic loading via .zip files enables second-level installation and uninstallation of features.
  • SDUI Ready: UI layouts are driven by backend protocols. Modifying elements only requires adjusting JSON — no app store resubmission.
  • Atomic Decoupling: Plugins communicate via an event bus, working together or independently.

Features

🔌

Plugin Management

Dynamically upload and extract plugin packages via the Dashboard. Server auto-restarts to load new plugin routes.

🔄

Dynamic Route Injection

The core auto-scans and registers API routes defined within the plugin package with automatic prefixing.

🗃

Extensible Data Model

PostgreSQL + JSONB allows plugins to store private metadata without altering core table structures.

📋

JSON Schema

Plugins declare tables via manifest.json schema — the core auto-creates and syncs PostgreSQL tables.

🔃

SQL Migrations

Plugins ship .sql migration files; the core tracks and applies them incrementally.

🗣

i18n Support

Plugin response messages, schema, KV store, and error handling are fully localized with locale resolution.

🔒

Auth & Permissions

Built-in token-based authentication with role-based permission guards and wildcard matching.

📱

Cross-Platform Protocol

A unified JSON protocol drives rendering for both Flutter and Web clients.

Quick Start

# 1. Install dependencies
npm install

# 2. Configure environment
cp .env.example .env
# Edit .env and set DATABASE_URL

# 3. Initialize the database
npx prisma migrate deploy

# 4. Generate the Prisma client
npx prisma generate

# 5. Start the server
npm run start:dev

# 6. Server runs at http://localhost:3000
#    Plugins are stored in ./storage/plugins/
💡 First User = Admin
The first user to register automatically gets the ADMIN role with ["*"] (all) permissions. Subsequent users get the USER role with no permissions.

Test with the Sample Plugin

# ZIP the sample plugin (include manifest.json, dist/, and optional locales/ / migrations/)
cd sample-plugins/test-plugin && zip -r ../../test-plugin.zip manifest.json dist/

# Install via API
curl -X POST -F "file=@test-plugin.zip" http://localhost:3000/plugins/upload

# Verify it is installed
curl http://localhost:3000/plugins

# Test the plugin routes
curl http://localhost:3000/test-plugin/status
📦 Packaging plugins with locales/ or migrations/
If your plugin includes i18n translations or SQL migrations, include those directories in the ZIP: 
cd sample-plugins/test-multilang-db-plugin
zip -r ../../test-multilang-db-plugin.zip manifest.json dist/ locales/ migrations/

1. PrismaModule src/prisma/

Marked @Global() so PrismaService is injectable everywhere without explicit import.

  • Creates a PrismaClient backed by a pg.Pool from DATABASE_URL via @prisma/adapter-pg.
  • Implements OnModuleDestroy to gracefully disconnect on shutdown.
  • Exposes client for direct model access (no repository pattern).
  • Provides query(sql, params?) for raw SQL execution via the pg pool.

2. PluginLoaderModule src/plugins/

A dynamic module with a static forRoot(pluginsDir) factory. Runs at bootstrap time and scans the filesystem.

  • Enumerates storage/plugins/<name>/dist/index.js, falling back to index.js
  • Uses Reflect.getMetadata('controllers', PluginModule) to detect controller paths
  • Auto-prefixes routes with manifest name (e.g. /test-plugin/status)
  • Detects and throws on duplicate controller routes across plugins
  • Reads manifest.auth and applies isPublic metadata when auth.required === false
  • Imports valid plugin modules into the NestJS module graph
⚠️ Filesystem-based
Because this module runs in a static factory, it cannot use the database as its source of truth. After install/update/uninstall, the server auto-restarts to reload routes.

💡 i18n KV Pattern
Store set(plugin, key, {title:"Hello"}, {i18nPaths:["title"]}) → saves {title:{"en":"Hello"}}. A second call with locale zh-CN merges: {title:{"en":"Hello","zh-CN":"你好"}}. Read with get(..., {i18nPaths:["title"]}) returns {title:"Hello"} for English users.

9. I18nModule src/i18n/

Marked @Global() so I18nService is injectable everywhere. Applies I18nMiddleware to all routes, reading the Accept-Language request header and scoping the resolved locale to the current request via AsyncLocalStorage. The default locale is en.

Core locale files live under locales/{locale}/*.json. Plugins register additional translations at install time and deregister them on uninstall.

Authentication & Authorization Overview

Wau Core includes a complete token-based authentication and role-based authorization system built from scratch (no external auth libraries like Passport or JWT). Two global guards are registered as APP_GUARD providers in AppModule:

  • AuthGuard — Validates Bearer tokens on every request (unless marked @Public())
  • PermissionGuard — Checks required permissions on routes decorated with @RequirePermissions()
graph LR subgraph Req["Incoming Request"] A["AuthGuard"] B["PermissionGuard"] end A -->|"Valid token?"| C["request.user = UserPayload"] C --> B B -->|"Has permission?"| D["Route Handler"] B -->|"No permission"| E["403 Forbidden"] A -->|"Invalid/missing"| F["401 Unauthorized"]

AuthService src/auth/auth.service.ts

Core authentication logic implementing token-based auth with bcrypt password hashing.

Key Features

  • Token-based auth: Creates random 32-byte hex tokens stored in userToken table with configurable TTL (default 7d)
  • Auto-cleanup: Cron job runs every 6 hours to clean up expired/revoked tokens
  • First-user admin: First registered user gets ADMIN role with ["*"] permissions
  • Role sync: On startup, ensures ADMIN and USER roles have correct permissions

Permission System

Permissions are stored as a JSON array on the Role model. The PermissionGuard supports wildcard matching:

  • * — grants all permissions
  • plugin:* — grants all permissions starting with plugin:
  • plugin:create — exact match

Plugin Auth Metadata

Plugins can declare auth configuration in manifest.json:

{
  "name": "my-plugin",
  "version": "1.0.0",
  "auth": {
    "required": false
  }
}

When auth.required === false, the PluginLoaderModule automatically marks all route handler methods on the plugin's controllers as isPublic: true, making them bypass AuthGuard.

⚠️ Permissions are Informational
manifest.auth.permissions is intentionally not enforced by the core. Permissions declared in manifest.json are purely informational. Actual enforcement requires explicit @RequirePermissions(...) decorators on each route handler.

Plugin Structure

A valid Wau plugin is a ZIP archive with this structure:

my-plugin.zip
├── manifest.json          # Plugin metadata
├── dist/
│   └── index.js           # Plugin entry point (fallback: index.js at root)
├── locales/               # Optional: i18n translation files
│   ├── en/
│   │   ├── messages.json
│   │   └── errors.json
│   └── zh-CN/
│       ├── messages.json
│       └── errors.json
└── migrations/            # Optional: SQL migration files
    └── 20260101000000_init.sql

manifest.json

Required fields: name, version. All others are optional.

{
  "name": "my-plugin",
  "version": "1.0.0",
  "description": "What this plugin does",
  "author": "Your Name",
  "auth": {
    "required": true,
    "permissions": ["plugin:read"]
  },
  "i18n": {
    "defaultLocale": "en",
    "locales": ["en", "zh-CN", "ms-MY"],
    "path": "./locales"
  },
  "schema": {
    "articles": {
      "title":   { "type": "string", "required": true, "i18n": true },
      "content": { "type": "text",   "i18n": true },
      "slug":    { "type": "string", "required": true, "unique": true, "length": 100 },
      "status":  { "type": "string", "required": true, "default": "draft", "index": true }
    }
  }
}
FieldRequiredDescription
nameYesUnique plugin identifier. Used as route prefix and table name prefix.
versionYesSemver string. Install rejects same-version or downgrade uploads.
descriptionNoHuman-readable description.
authorNoAuthor name.
authNoAuth metadata. required: false makes all plugin routes public.
i18nNoDeclares i18n support. defaultLocale, locales, path (default ./locales).
schemaNoJSON schema for dynamic table creation via PluginSchemaService.

i18n (Translations)

If the extracted plugin contains a locales/ directory, the core automatically calls I18nService.registerPluginLocale() at install/update time and unregisterPluginLocale() on uninstall.

Locale files are plain JSON under locales/{locale}/{file}.json. Two layouts are supported:

// Flat layout
{
  "welcome": "Welcome!",
  "created": "Record created."
}

// Wrapped layout (sole top-level key matches filename, auto-unwrapped)
{
  "messages": {
    "welcome": "Welcome!",
    "created": "Record created."
  }
}

Both are accessible as i18n.tPlugin(pluginName, 'messages.welcome') or from core code as i18n.t('{pluginName}.messages.welcome'). Placeholder interpolation uses {key} syntax.

JSON Schema

Declare a schema object in manifest.json to have PluginSchemaService automatically create and sync PostgreSQL tables. Table names are prefixed plugin_{name}_{model}.

Add "i18n": true to any field to store it as a JSONB locale map. Reads via find() / findOne() automatically return the flattened value for the request locale.

SQL Migrations

Plugins can include a migrations/ directory with .sql files named with a sortable timestamp prefix (e.g. 20260101000000_create_table.sql). Files are executed in alphabetical order on install/update. Applied filenames are tracked in plugin_registry.migrations_applied to prevent re-runs. On uninstall, tables prefixed plugin_{name}_* are dropped automatically.

Building & Packaging

Compile TypeScript to dist/ and export the NestJS module class from the entry point:

// dist/index.js (compiled from index.ts)
export { MyPluginModule } from './src/my-plugin.module';

The ZIP should contain manifest.json, dist/, and optionally locales/ and migrations/. Do not include TypeScript source, node_modules, or build config files.

Plugin Management API

GET /plugins

Permission: plugin:read

List all installed plugins from the database.

Response: Array of { name, version, description, author, manifest, migrationsApplied, createdAt, updatedAt }

POST /plugins/upload

Permission: plugin:create

Body: multipart/form-data with file (ZIP)

Fresh install if plugin does not exist. Auto-update if uploaded version is higher. Rejected if same version or downgrade.

Response (install): { success, plugin, version, path, message }

Response (update): { success, plugin, previousVersion, version, path, message }

PUT /plugins

Permission: plugin:update

Body: multipart/form-data with file (ZIP)

Update an installed plugin. Plugin name is auto-detected from the ZIP manifest.json. Same validation and behavior as upload when the plugin already exists.

DELETE /plugins/:name

Permission: plugin:delete

Uninstall a plugin by name. Cleans up schema tables, migrations, and plugin_data entries.

Response: { success, plugin, message }

💡 Core vs. Plugin Migrations
Core Prisma migrations only manage plugin_registry, plugin_data, users, roles, and user_tokens tables. Plugin-owned tables are created at plugin install time by PluginSchemaService (from manifest.json schema) and PluginMigrationService (from migrations/*.sql). These two systems are independent.

Future Roadmap

Wau is designed as a full-stack plugin platform. The backend core is just the beginning:

  • Flutter Client (wau-flutter) — A mobile app shell that dynamically renders screens from JSON protocols served by plugins.
  • React JS Web App (wau-web) — A dual-purpose React application: an admin dashboard for managing plugins and a user-facing client.
  • Event Bus — Cross-plugin & cross-platform communication so backend plugins can trigger actions in Flutter and Web clients.
  • SDUI Protocol — Backend-driven layout engine for fully dynamic UI generation.
