Wau Core Documentation

Wau Core is a NestJS-based plugin runtime engine. It scans and loads third-party plugin modules at boot time via PluginLoaderModule, while persisting plugin metadata in a PostgreSQL database via Prisma. The server auto-restarts after plugin install/update/uninstall to reload routes.

Module Breakdown

1. PrismaModule src/prisma/

Marked @Global() so PrismaService is injectable everywhere without explicit import.

  • PrismaService creates a PrismaClient backed by a pg.Pool from DATABASE_URL.
  • Implements OnModuleDestroy to gracefully disconnect on shutdown.
  • Exposes client for direct model access (no repository pattern).

2. PluginLoaderModule src/plugins/plugin-loader.module.ts

A dynamic module with a static forRoot(pluginsDir) factory. It runs at application bootstrap time (before DI is fully ready) and therefore scans the filesystem.

Responsibilities:

  • Enumerate storage/plugins/<name>/dist/index.js, falling back to storage/plugins/<name>/index.js if dist/ is absent
  • Use Reflect.getMetadata('controllers', PluginModule) to detect controller paths
  • Auto-prefix routes with manifest name (e.g. /test-plugin/status)
  • Detect and throw on duplicate controller routes across plugins
  • Import valid plugin modules into the NestJS module graph
Because this module runs in a static factory, it cannot use the database as its source of truth. It remains filesystem-based. After install/update/uninstall, the server auto-restarts to reload routes.

5. PluginDataService src/plugin-data/plugin-data.service.ts

Key-value store for plugin runtime data. Wraps the PluginData model with an upsert-based API. All values are stored as JSONB. Fields can optionally carry i18n locale maps ({"en":"Hello","zh-CN":"你好"}) that are transparently resolved or merged on read/write.

7. PluginSchemaService src/plugin-schema/plugin-schema.service.ts

Provides dynamic table creation and CRUD operations driven by a JSON schema declared in manifest.json. Table names are prefixed plugin_{name}_{model}. Every table automatically gets id (SERIAL PRIMARY KEY), created_at, and updated_at columns.

SyntaxSQL equivalent

For i18n fields, WHERE comparisons automatically target the ->>'{locale}' JSONB text extraction, so {name: "Hello"} filters on the current-locale value.

8. I18nModule src/i18n/

Marked @Global() so I18nService is injectable everywhere. Applies I18nMiddleware to all routes, reading the Accept-Language request header and scoping the resolved locale to the current request via AsyncLocalStorage. The default locale is en.

Core locale files live under locales/{locale}/*.json. Plugins register additional translations at install time and deregister them on uninstall.

I18nService Methods

MethodDescription
t(key, args?)Translate a dot-notation key for the current request locale; falls back to en. Supports {placeholder} interpolation.

Locale File Layout

Core locale files (locales/en/messages.json, locales/en/errors.json, etc.) are flat JSON or nested objects. Plugin locale files follow the same convention but are placed inside the plugin zip under locales/{locale}/{file}.json:

locales/
├── en/
│   ├── errors.json      # Postgres error messages, plugin error strings
│   └── messages.json    # Success/status messages
└── zh-CN/
    ├── errors.json
    └── messages.json

Plugin translations are accessible as {pluginName}.{file}.{key}, e.g. my-plugin.messages.welcome.

Plugin Format Specification

A valid Wau plugin is a ZIP archive. The minimum structure is manifest.json + compiled dist/. Add locales/ for i18n and migrations/ for SQL migrations:

myplugin.zip
├── manifest.json               # Required — plugin metadata
├── dist/
│   └── index.js                # Required — compiled entry point (exports NestJS Module)
├── locales/                    # Optional — i18n translation files
│   ├── en/
│   │   ├── messages.json       # Success / status messages
│   │   └── errors.json         # Error messages
│   └── zh-CN/
│       ├── messages.json
│       └── errors.json
└── migrations/                 # Optional — SQL migration files (.sql)
    └── 20260101000000_init.sql

If dist/ is absent, the core falls back to index.js at the ZIP root.

manifest.json

Required fields: name, version. All others are optional.

{
  "name": "my-plugin",
  "version": "1.0.0",
  "description": "What this plugin does",
  "author": "Your Name"
}

With i18n support and a JSON schema:

{
  "name": "my-plugin",
  "version": "1.0.0",
  "description": "Multilingual plugin with dynamic tables",
  "author": "Your Name",
  "i18n": {
    "defaultLocale": "en",
    "locales": ["en", "zh-CN", "ms-MY"],
    "path": "./locales"
  },
  "schema": {
    "articles": {
      "title":   { "type": "string", "required": true, "i18n": true },
      "content": { "type": "text",   "i18n": true },
      "slug":    { "type": "string", "required": true, "unique": true, "length": 100 },
      "status":  { "type": "string", "required": true, "default": "draft", "index": true }
    }
  }
}
FieldRequiredDescription
nameYesUnique plugin identifier. Used as the route prefix and table name prefix.
versionYesSemver string. Install rejects same-version or downgrade uploads.
descriptionNoHuman-readable description.
authorNoAuthor name.
i18nNoDeclares i18n support. defaultLocale, locales (array), path (relative to ZIP root, default ./locales).
schemaNoJSON schema for dynamic table creation via PluginSchemaService.

i18n (Translations)

If the extracted plugin contains a locales/ directory, the core automatically calls I18nService.registerPluginLocale() at install/update time and unregisterPluginLocale() on uninstall.

Locale files are plain JSON under locales/{locale}/{file}.json. Two layouts are supported:

// Flat layout — locales/en/messages.json
{
  "welcome": "Welcome!",
  "created": "Record created."
}

// Wrapped layout — locales/en/messages.json
// (sole top-level key matches filename, so it is auto-unwrapped)
{
  "messages": {
    "welcome": "Welcome!",
    "created": "Record created."
  }
}

Both are accessible in the plugin as i18n.tPlugin(pluginName, 'messages.welcome') or from core code as i18n.t('{pluginName}.messages.welcome'). Placeholder interpolation uses {key} syntax: i18n.tPlugin(name, 'messages.hello', { name: 'Alice' }).

JSON Schema

Declare a schema object in manifest.json to have PluginSchemaService automatically create and sync PostgreSQL tables. Table names are prefixed plugin_{name}_{model}. Supported field types: string, int, bigint, float, decimal, boolean, date, timestamp, json, text.

Add "i18n": true to any field to store it as a JSONB locale map ({"en":"Hello","zh-CN":"你好"}). Reads via find() / findOne() automatically return the flattened value for the request locale.

SQL Migrations

Plugins can include a migrations/ directory with .sql files named with a sortable timestamp prefix (e.g. 20260101000000_create_table.sql). Files are executed in alphabetical order on install/update. Applied filenames are tracked in plugin_registry.migrations_applied to prevent re-runs. On uninstall, tables prefixed plugin_{name}_* are dropped automatically.

Built Output

Compile TypeScript to dist/ and export the NestJS module class from the entry point:

// dist/index.js  (compiled from index.ts)
export { MyPluginModule } from './src/my-plugin.module';

The ZIP should contain manifest.json, dist/, and optionally locales/ and migrations/. Do not include TypeScript source, node_modules, or build config files.

PluginRegistry Database Migration

What Changed

Prior to this migration, PluginManagerService relied solely on an in-memory Map and filesystem scanning of manifest.json files. The PluginRegistry Prisma model existed in the schema but was never used by application code.

New Data Flow

flowchart LR Op["PluginController\nInstall / Update / Uninstall"] --> Mgr["PluginManagerService\nValidate ZIP\nExtract to FS\nTrigger restart\nPersist to DB"] Mgr <--> PR[("plugin_registry\nPostgreSQL")] Mgr --> FS["storage/plugins/\nCode files"]

Consistency Strategy

ScenarioBehavior
DB record exists, code existsNormal load at startup
DB record exists, code missingWarn and skip (orphaned DB record)
Code exists, DB record missingIgnored by PluginManagerService; PluginLoaderModule still loads NestJS module. Re-install to create DB record.

Rollback Behavior

OperationRollback on Failure
Install (route conflict)Delete extracted directory + delete DB record
Update (route conflict)Delete new extraction. Old code already deleted; DB updated to new version. This is an architectural limitation.
UninstallDB record deleted first, then directory. If directory deletion fails, filesystem orphan remains.

Prisma Setup & Deployment

Wau Core uses Prisma 7 with the @prisma/adapter-pg adapter against PostgreSQL. The schema is split across multiple files under prisma/schema/ and migrations are stored in prisma/migrations/. The Prisma config is in prisma.config.ts:

import { defineConfig, env } from 'prisma/config'
import { config } from 'dotenv'
import { resolve } from 'path'

config({ path: resolve(__dirname, '.env') })

export default defineConfig({
  schema: './prisma/schema',
  migrations: { path: './prisma/migrations' },
  datasource: { url: env('DATABASE_URL') },
})

Prerequisites

  • PostgreSQL 14+ running and reachable
  • Node.js 20+ and npm
  • .env file with a valid DATABASE_URL (copy from .env.example)

Local Development

# Install dependencies (runs prisma generate via postinstall if configured)
npm install

# Configure your database URL
cp .env.example .env
# edit .env -> DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DB_NAME?schema=public

# Apply all migrations to the local database
npx prisma migrate deploy

# Generate the Prisma client
npx prisma generate

# Run the dev server
npm run start:dev

Creating a New Migration

When you change a model in prisma/schema/plugin.prisma (or add a new .prisma file), create a migration with:

npx prisma migrate dev --name <short_description>

This generates a new folder under prisma/migrations/<timestamp>_<name>/ containing a single migration.sql. Commit both the schema change and the new migration folder.

Production Deployment

Production deploys should never use migrate dev (which is interactive and can drop data). Use migrate deploy instead:

# 1. Apply pending migrations (non-interactive, safe for prod / CI)
npx prisma migrate deploy

# 2. Generate the Prisma client (typically already part of postinstall)
npx prisma generate

# 3. Build and start
npm run build
npm run start:prod

Useful Commands

CommandPurpose
npx prisma migrate dev --name <n>Create + apply a new migration locally

The core Prisma migrations only manage the plugin_registry and plugin_data tables. Plugin-owned tables are created at plugin install time by PluginSchemaService (from manifest.json schema) and PluginMigrationService (from migrations/*.sql). These two systems are independent and tracked separately in plugin_registry.migrations_applied.
