Wau Core 文档

Wau Core 是一个基于 NestJS 的插件运行时引擎。它通过 PluginLoaderModule 在启动时扫描并加载第三方插件模块，同时通过 Prisma 将插件元数据持久化到 PostgreSQL 数据库。插件安装/更新/卸载后，服务器自动重启以重新加载路由。

技术栈

层级技术
框架NestJS 11
数据库PostgreSQL
ORMPrisma 7 + @prisma/adapter-pg
HTTPExpress（通过 NestJS platform-express）
配置@nestjs/config
工具库fs-extra, adm-zip

模块详解

1. PrismaModule src/prisma/

标记为 @Global()，因此 PrismaService 可以在任何地方注入，无需显式导入。

  • PrismaService 通过 pg.Pool 从 DATABASE_URL 创建 PrismaClient。
  • 实现 OnModuleDestroy，在关闭时优雅断开连接。
  • 暴露 client 属性直接访问模型（无仓库模式）。

2. PluginLoaderModule src/plugins/plugin-loader.module.ts

一个带有静态 forRoot(pluginsDir) 工厂方法的动态模块。它在应用启动时运行（此时依赖注入尚未完全就绪），因此扫描文件系统。

职责：

  • 枚举 storage/plugins/<name>/dist/index.js，若不存在则回退到 storage/plugins/<name>/index.js
  • 使用 Reflect.getMetadata('controllers', PluginModule) 检测控制器路径
  • 以 manifest name 为前缀自动拼接路由（如 /test-plugin/status）
  • 检测并拦截跨插件重复的控制器路由
  • 将有效插件模块导入 NestJS 模块图
由于该模块在静态工厂中运行，无法以数据库作为数据源。它保持基于文件系统的实现。插件安装/更新/卸载后，服务器会自动重启以重新加载路由。

5. PluginDataService src/plugin-data/plugin-data.service.ts

插件运行时键值数据存储。通过 upsert API 包装 PluginData 模型。所有值以 JSONB 存储。字段可选择携带 i18n locale 映射（{"en":"Hello","zh-CN":"你好"}），在读写时自动解析或合并。

方法签名说明
getget(plugin, key, options?)读取单个键值条目。options.resolveI18n 自动将所有 locale 映射扁平化为当前 locale。options.i18nPaths（点分隔路径数组）仅解析指定字段。options.lang 覆盖请求 locale。
setset(plugin, key, data, options?)创建或覆盖键值条目。options.i18nPaths 在创建时将指定路径的字符串值包装为 {locale: value}；在更新时将新 locale 合并到已有 JSONB 中。
removeremove(plugin, key)删除键值条目。
listlist(plugin, options?)列出某插件的所有键值条目。支持与 get 相同的 resolveI18n / i18nPaths / lang 选项。
resolveI18nValueresolveI18nValue(jsonb, locale?)工具方法：将 JSONB locale 映射解析为单一字符串，回退到 en，再回退到第一个可用键。
queryRawqueryRaw<T>(query, params?)对插件自有表执行原始 SELECT 查询（供迁移模式插件使用）。
executeRawexecuteRaw(query, params?)对插件自有表执行原始写入查询（供迁移模式插件使用）。
i18n KV 示例：set(plugin, key, {title:"Hello"}, {i18nPaths:["title"]}) 存储 {title:{"en":"Hello"}}。在 zh-CN locale 下再次调用后合并为 {title:{"en":"Hello","zh-CN":"你好"}}。读取时使用 get(..., {i18nPaths:["title"]})，英文用户得到 {title:"Hello"}。

7. PluginSchemaService src/plugin-schema/plugin-schema.service.ts

通过 manifest.json 中声明的 JSON schema 动态创建表并提供 CRUD 操作。表名前缀为 plugin_{name}_{model}。每张表自动添加 id（SERIAL PRIMARY KEY）、created_at、updated_at 列。

8. I18nModule src/i18n/

标记为 @Global()，I18nService 可在任何地方注入。对所有路由应用 I18nMiddleware，读取请求的 Accept-Language 头，通过 AsyncLocalStorage 将解析出的 locale 绑定到当前请求作用域。默认 locale 为 en。

核心 locale 文件存放在 locales/{locale}/*.json。插件在安装时注册各自的翻译，在卸载时注销。

I18nService 方法

方法说明
t(key, args?)按点分隔键翻译当前请求的 locale；回退到 en。支持 {placeholder} 插值。
tPlugin(pluginName, key, args?)t('{pluginName}.{key}') 的快捷方式，翻译插件命名空间下的键。
getLocale()从 AsyncLocalStorage 返回当前请求 locale，无则返回 en。
registerPluginLocale(name, dir)加载 {dir}/{locale}/*.json 并将键合并到 {name}.* 命名空间下，返回已注册的键列表供清理使用。
unregisterPluginLocale(name)移除该插件命名空间下的所有翻译。

Locale 文件结构

核心 locale 文件（locales/en/messages.json、locales/en/errors.json 等）为平铺或嵌套 JSON。插件 locale 文件放在 ZIP 包内 locales/{locale}/{file}.json：

locales/
├── en/
│   ├── errors.json      # Postgres 错误消息、插件错误字符串
│   └── messages.json    # 成功/状态消息
└── zh-CN/
    ├── errors.json
    └── messages.json

插件翻译通过 {pluginName}.{file}.{key} 访问，例如 my-plugin.messages.welcome。

插件格式规范

一个有效的 Wau 插件是一个 ZIP 压缩包。最小结构为 manifest.json + 编译后的 dist/。可选添加 locales/ 支持 i18n，或 migrations/ 支持 SQL 迁移：

myplugin.zip
├── manifest.json               # 必需 — 插件元数据
├── dist/
│   └── index.js                # 必需 — 编译后入口文件（导出 NestJS 模块）
├── locales/                    # 可选 — i18n 翻译文件
│   ├── en/
│   │   ├── messages.json       # 成功 / 状态消息
│   │   └── errors.json         # 错误消息
│   └── zh-CN/
│       ├── messages.json
│       └── errors.json
└── migrations/                 # 可选 — SQL 迁移文件
    └── 20260101000000_init.sql

若不存在 dist/，核心回退到 ZIP 根目录的 index.js。

manifest.json

必需字段：name、version。其余均为可选。

{
  "name": "my-plugin",
  "version": "1.0.0",
  "description": "插件描述",
  "author": "作者名称"
}

带 i18n 支持与 JSON schema 的完整示例：

{
  "name": "my-plugin",
  "version": "1.0.0",
  "description": "多语言插件，含动态数据表",
  "author": "作者名称",
  "i18n": {
    "defaultLocale": "en",
    "locales": ["en", "zh-CN", "ms-MY"],
    "path": "./locales"
  },
  "schema": {
    "articles": {
      "title":   { "type": "string", "required": true, "i18n": true },
      "content": { "type": "text",   "i18n": true },
      "slug":    { "type": "string", "required": true, "unique": true, "length": 100 },
      "status":  { "type": "string", "required": true, "default": "draft", "index": true }
    }
  }
}
字段必需说明
name是插件唯一标识符，用作路由前缀和表名前缀。
version是语义化版本号。安装时拒绝相同版本或降级上传。
description否可读描述。
author否作者名称。
i18n否声明 i18n 支持。defaultLocale、locales（数组）、path（相对 ZIP 根目录，默认 ./locales）。
schema否JSON schema，用于通过 PluginSchemaService 动态建表。

i18n（多语言翻译）

若解压后的插件包含 locales/ 目录，核心会在安装/更新时自动调用 I18nService.registerPluginLocale()，在卸载时调用 unregisterPluginLocale()。

Locale 文件为纯 JSON，路径格式为 locales/{locale}/{file}.json。支持两种布局：

// 平铺布局 — locales/zh-CN/messages.json
{
  "welcome": "欢迎！",
  "created": "创建成功。"
}

// 包裹布局 — locales/zh-CN/messages.json
// （唯一顶层 key 与文件名一致时自动展开）
{
  "messages": {
    "welcome": "欢迎！",
    "created": "创建成功。"
  }
}

两种方式均可通过 i18n.tPlugin(pluginName, 'messages.welcome') 访问，或从核心代码使用 i18n.t('{pluginName}.messages.welcome')。占位符插值使用 {key} 语法：i18n.tPlugin(name, 'messages.hello', { name: 'Alice' })。

JSON Schema

在 manifest.json 中声明 schema 对象，由 PluginSchemaService 自动创建并同步 PostgreSQL 表。表名前缀为 plugin_{name}_{model}。支持字段类型：string、int、bigint、float、decimal、boolean、date、timestamp、json、text。

在任意字段上添加 "i18n": true 可将其存储为 JSONB locale 映射（{"en":"Hello","zh-CN":"你好"}）。通过 find() / findOne() 读取时，自动返回当前请求 locale 对应的扁平值。

SQL 迁移

插件可包含 migrations/ 目录，存放以可排序时间戳前缀命名的 .sql 文件（如 20260101000000_create_table.sql）。安装/更新时按字母顺序执行，执行记录在 plugin_registry.migrations_applied 中防止重复执行。卸载时自动删除前缀为 plugin_{name}_* 的表。

构建输出

将 TypeScript 编译到 dist/，并从入口文件导出 NestJS 模块类：

// dist/index.js（由 index.ts 编译生成）
export { MyPluginModule } from './src/my-plugin.module';

ZIP 中应包含 manifest.json、dist/，以及可选的 locales/ 和 migrations/。不要打包 TypeScript 源文件、node_modules 或构建配置文件。

PluginRegistry 数据库迁移

变更内容

迁移前，PluginManagerService 仅依赖内存中的 Map 和文件系统扫描 manifest.json。虽然 PluginRegistry Prisma 模型已存在于 schema 中，但应用代码从未使用它。

新数据流

flowchart LR Op["PluginController\n安装 / 更新 / 卸载"] --> Mgr["PluginManagerService\n验证 ZIP\n解压到文件系统\n触发重启\n持久化到数据库"] Mgr <--> PR[("plugin_registry\nPostgreSQL")] Mgr --> FS["storage/plugins/\n代码文件"]

一致性策略

场景行为
数据库有记录，代码存在启动时正常加载
数据库有记录，代码缺失警告并跳过（孤立的数据库记录）
代码存在，数据库无记录PluginManagerService 忽略；PluginLoaderModule 仍会加载 NestJS 模块。重新安装可补录数据库记录。

回滚行为

操作失败时的回滚
安装（路由冲突）删除已解压目录 + 删除数据库记录
更新（路由冲突）删除新解压的目录。旧代码已被删除；数据库已更新到新版本。这是架构限制。
卸载先删除数据库记录，再删除目录。若目录删除失败，文件系统残留孤儿文件。

Prisma 配置与部署

Wau Core 基于 Prisma 7，使用 @prisma/adapter-pg 适配器连接 PostgreSQL。Schema 拆分在 prisma/schema/ 下的多个文件中，迁移文件位于 prisma/migrations/。Prisma 配置位于 prisma.config.ts：

import { defineConfig, env } from 'prisma/config'
import { config } from 'dotenv'
import { resolve } from 'path'

config({ path: resolve(__dirname, '.env') })

export default defineConfig({
  schema: './prisma/schema',
  migrations: { path: './prisma/migrations' },
  datasource: { url: env('DATABASE_URL') },
})

前置条件

  • PostgreSQL 14+ 正在运行且可访问
  • Node.js 20+ 与 npm
  • .env 文件包含可用的 DATABASE_URL（可从 .env.example 复制）

本地开发

# 安装依赖（若配置了 postinstall，会自动执行 prisma generate）
npm install

# 配置数据库 URL
cp .env.example .env
# 编辑 .env -> DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DB_NAME?schema=public

# 应用所有迁移到本地数据库
npx prisma migrate deploy

# 生成 Prisma 客户端
npx prisma generate

# 启动开发服务器
npm run start:dev

创建新迁移

当你修改 prisma/schema/plugin.prisma 中的模型（或新增 .prisma 文件）时，使用以下命令创建迁移：

npx prisma migrate dev --name <简短描述>

该命令会在 prisma/migrations/<时间戳>_<名称>/ 下生成新的目录，包含一个 migration.sql 文件。请将 schema 变更和新的迁移目录一起提交。

生产部署

生产环境部署绝不应使用 migrate dev（它是交互式的，可能会丢失数据）。请使用 migrate deploy：

# 1. 应用待执行的迁移（非交互式，适用于生产 / CI）
npx prisma migrate deploy

# 2. 生成 Prisma 客户端（通常已包含在 postinstall 中）
npx prisma generate

# 3. 构建并启动
npm run build
npm run start:prod

常用命令

命令用途
npx prisma migrate dev --name <n>开发环境创建并应用新迁移
npx prisma migrate deploy应用待执行的迁移（生产 / CI）
npx prisma migrate status查看已应用与待执行的迁移
npx prisma generate重新生成 Prisma 客户端
npx prisma studio通过本地 GUI 浏览数据
npx prisma migrate reset删除数据库并重新应用所有迁移（破坏性操作）
核心 Prisma 迁移只负责 plugin_registry 和 plugin_data 两张表。插件自有的表是在插件安装时由 PluginSchemaService（基于 manifest.json 中的 schema）和 PluginMigrationService（基于 migrations/*.sql）创建的。这两套系统相互独立，已应用的迁移记录在 plugin_registry.migrations_applied 字段中。
